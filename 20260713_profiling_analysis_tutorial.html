TUTORIAL: HOW TO GENERATE AND ANALYZE AUDIO ENGINE CPU PROFILES

This tutorial provides a step-by-step guide for developers to reproduce, extract, and analyze performance profile data for the rust-firework audio engine. It explains how the insights from the profiling report were gathered using the Linux perf tool and the Hotspot GUI.

1. Prerequisites

To profile the audio engine, you need a Linux environment with the following tools installed:

  1. perf: The Linux profiling tool. Install it via your package manager (e.g., sudo apt install linux-tools-generic).
  2. hotspot: A GUI visualizer for perf.data files. Install it via your package manager (e.g., sudo apt install hotspot) or download the AppImage.
  3. Debug Symbols Enabled: Ensure your Cargo.toml is configured to include debug symbols even in release mode (otherwise, function names/symbols in the profile will be shown as hex addresses or [unknown]): 
    [profile.release]
debug = true # Crucial for profiling!

2. Step 1: Generating the Performance Profile (perf.data)

The profile is generated by running the application under perf record while running the headless audio stress-test.

Option A: Using the Task runner (Recommended)

We have a pre-configured task runner helper. Run:

task hotspot-audio

Note: This command runs the profile generation and then attempts to launch the Hotspot GUI.

Option B: Running raw commands manually

To record the profile manually for 10 seconds of simulation:

# 1. Run the release binary under perf record
perf record -g --call-graph dwarf -F 997 -o target/perf_audio_doppler.data -- target/release/fireworks_sim --headless-audio-stress 10

Parameters explained:

  • -g --call-graph dwarf: Records the call graph (stack traces) using DWARF symbols. This allows reconstruction of function call trees.
  • -F 997: Samples at 997 Hz (not exactly 1000 Hz to avoid lockstep synchronization with system timers, which can bias the results).
  • -o target/perf_audio_doppler.data: Outputs the binary profile results to this file.
  • --headless-audio-stress 10: Tells the application to bypass window creation and run 128 active voices for 10 seconds to saturate the audio DSP loop.

3. Step 2: Analyzing the Profile in CLI (Text Mode)

If you are working via SSH or prefer the command line, you can generate text reports from perf.data.

A. View the Hotspot Hierarchy (Call Tree)

To see where the CPU spends its time in relation to parent/child calls, run:

perf report -i target/perf_audio_doppler.data --stdio --percent-limit 0.5
  • --stdio: Outputs to terminal stdout instead of starting an interactive TUI.
  • --percent-limit 0.5: Cops the output to only show paths taking more than 0.5% CPU, which keeps the text output clean and readable.

What to look for: Find the ALSA thread worker cpal_alsa_out and inspect the call tree down to DspProcessor::process_dsp. You will see:

cpal_alsa_out (Thread)
└── output_stream_worker (CPAL worker)
    └── build_output_stream (Callback)
        ├── DspProcessor::process_dsp  <-- Our core DSP mixing loop (should be the highest)
        └── DspProcessor::write_cpal_buffer <-- Output copy & clipping stage

B. View the Flat Symbol List (Self Time)

To see which individual functions are taking the most CPU cycles directly (without call tree context), disable call graphs:

perf report -i target/perf_audio_doppler.data --stdio --percent-limit 0.1 --no-call-graph

How to read the columns:

  • Children %: The total percentage of cycles spent inside this function and all of the functions it calls.
  • Self %: The percentage of cycles spent exclusively executing code within this function body.

4. Step 3: Extracting Key Insights (How to read the numbers)

When analyzing the output of perf report, check these three key real-time audio indicators:

A. The "Self" vs "Children" percentage of process_dsp

  • In the flat view, locate DspProcessor::process_dsp.
  • Insight: If Self % and Children % are nearly identical (e.g., Children: 54.31%, Self: 53.80%), it means the DSP logic is extremely self-contained. The thread spends its time running the inner loop directly rather than jumping in and out of helper functions.

B. The cost of mathematical functions (libm.so)

Locate mathematical symbols like __powf_fma, __expf_fma, __sinf_fma, and __atan2f_finite:

  • Block-Rate Validation: Since we calculate these variables (ITD/ILD, distance, filter frequencies) once per block (~5 ms) instead of once per sample (1/48,000 s), their total CPU overhead should be extremely low (each should be < 1.5%).
  • Anomalies: If any of these math functions are taking > 5% CPU, check if they were accidentally placed inside the sample-by-sample loop instead of the block-level setup.

C. Checking for Memory Allocations (Real-Time Safety)

Real-time audio callback threads must be lock-free and heap-allocation-free.

  • Test: Search the symbols list for malloc, free, realloc, jemalloc, mutex_lock, or pthread_mutex_lock.
  • Result: For a healthy real-time thread, these functions should not appear at all in the list of hotspots, verifying that our zero-allocation design is functioning correctly under load.

5. Step 4: Visualizing in Hotspot GUI (GUI Mode)

To get a graphical visualization, launch hotspot and open the file:

hotspot target/perf_audio_doppler.data

GUI Tabs to Use:

  1. Flame Graph: Look at the horizontal blocks. The wider a block is, the more CPU cycles it consumes. Verify that DspProcessor::process_dsp is a wide, flat column at the top of the stack.
  2. Top Functions: Check the "Self" column to identify code hotspots.
  3. Caller/Callee: Select DspProcessor::process_dsp to see exactly which operations (e.g. math functions or index interpolation) consume its execution budget.
  4. Source Code View: Double-click on DspProcessor::process_dsp. Hotspot will show the Rust code side-by-side with compiled assembly instructions. It colors the lines based on instruction density, showing you the exact lines of code (such as the LERP interpolation math) that are consuming the most CPU cycles.
